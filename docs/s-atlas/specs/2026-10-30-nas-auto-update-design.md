# NAS 稳定版自动更新设计

日期：2026-10-30。状态：用户已确认实施并发布到 `Acefake/yingbox`。

## 目标

NAS 首次部署或迁移后自动接收影盒稳定版，不再要求用户逐次修改版本号。桌面版和完整片库服务保持现有更新方式。

## 方案比较

1. 推荐使用稳定版镜像标签和独立 Watchtower 服务。用户只需替换一次 Compose；更新服务定时拉取镜像并重建影盒容器。需要 Docker 管理权限。
2. 使用 NAS 计划任务执行 Compose 拉取与重建。没有常驻更新服务，但绿联、群晖等设备的任务入口和权限配置不同，需要用户另外配置。
3. 在影盒网页中实现 Docker 更新接口。需要让应用获得 Docker 管理权限，还要新增鉴权、更新状态和故障恢复逻辑，超出当前需求。

## 部署行为

NAS Compose 默认使用 `ghcr.io/acefake/yingbox-nas:stable`。保留 `YINGBOX_VERSION` 覆盖项，指定明确版本时可以固定版本；环境变量示例使用 `stable`。升级已有安装需要替换一次部署文件，并将原来的固定版本设置改成 `stable`，后续不用修改版本号。

同一 Compose 增加更新服务，使用仍维护的 `nicholas-fedor/watchtower`，固定已核对版本及多架构镜像摘要。更新服务不自动更新自身。安装时验证 amd64、arm64 镜像可拉取。

更新服务按 `Asia/Shanghai` 时区每天 04:00 检查一次。仅选择名称为 `yingbox-nas`、启用更新标签且 scope 为 `yingbox-nas` 的容器。停止状态的容器保持停止。不选择其他容器。更新服务不公开网络管理端口。

影盒应用继续以非 root 用户运行，不挂载 Docker socket。只有独立更新服务挂载 `/var/run/docker.sock`。容器名、标签和 scope 是更新目标筛选，不是 Docker 权限隔离；更新服务本身持有管理 Docker 的权限。

原有 `/config`、`/cache` 和媒体挂载保持原路径。更新服务拉取成功后才停止旧容器，使用原有参数重建，给予服务正常退出的等待时间。更新期间网页和播放连接可能短暂中断。拉取失败时旧容器继续运行，下次检查重试。

不自动删除旧镜像、不删除数据卷、不宣称支持自动回退。新版本启动失败会留下 Docker 健康状态与更新日志，需要根据记录固定回原版本。数据库已迁移时，回退还可能需要恢复对应配置备份；上线有数据库迁移的版本前必须完成兼容性与恢复检查。

## 本机发布

继续在本机构建和发布，不依赖 GitHub Actions。每个版本保留不可重复使用的版本标签；只有 amd64、arm64 验证通过后才能把 `stable` 指向该版本的多架构索引。

首次发布 `stable` 时复用已经验证的 `1.0.0-nas.1` 多架构索引，不重新构建应用。核对 `stable` 的索引摘要和平台摘要均与版本镜像一致，验证匿名拉取。

增加可重复执行的本机稳定版发布入口，检查版本格式、目标索引和双架构，执行容器验证后更新 `stable`，并在更新前后记录摘要。更新部署说明中的发布方式，提供新的部署压缩包。

用新增 ADR 记录对 ADR-0024 固定版本默认部署方式的局部替代。保留既有 Windows 安装包、更新仓库和 NAS 应用功能。

## 验收

- Compose 展开后默认使用 `stable`，更新服务使用固定版本和摘要，定时规则及目标选择有效。
- 在隔离的临时 Docker 环境模拟镜像升级，证明影盒测试容器自动替换、挂载文件保留，未标记的对照容器不被重建，手动停止的容器不会启动。
- 模拟无更新和拉取失败，确认旧容器不被重建或停止。
- 实测当前影盒镜像经更新服务重建后健康检查通过，配置目录和片库数据可读；不使用用户真实媒体或登录数据。
- 验证两种架构镜像可用，公开 `stable` 与已发布版本的摘要相同。
- 自审全部差异，再按仓库要求派只读子代理独立审查；交付时区分本机验证与用户 NAS 真机验证。
