# HDR、杜比视界与全端画质增强实施方案

> 执行方式：2026-11-04 用户授权在新分支开发，当前分支为 `feat/hdr-playback-diagnostics`。由主任务逐阶段执行；实现完成后按项目规则自审和只读独立评审。提交与发布未授权。探索阶段的结果决定后续实现范围。

**目标：** 安卓手机和电视在能力允许时正确播放 HDR 与杜比视界，并在各端按实际能力提供画质增强。

**架构：** 安卓保留 Media3 与 SurfaceView 的原生播放路径；桌面继续使用现有 mpv 与内置播放器。各端统一能力和状态的含义，平台适配各自实现。超分是可关闭的附加处理，不能破坏正常播放。

**技术栈：** Kotlin、Media3、Compose、Electron、TypeScript、mpv；GPU shader、浏览器 GPU 处理和服务端转码均通过原型验证后再接入。

**验证与授权：** 已授权分阶段继续实现。纯决策逻辑使用单测，解码和显示使用真机；编译成功不代表 HDR/DV 验收通过。未授权提交或发布。

- 同目录 `StatsCollector.kt` 已记录实际解码器名和丢帧，适合扩展诊断。

## 2. 播放原则

1. 将片源信息、设备能力、播放计划、运行观察四类数据分开。能力未知使用 unknown，不能默认为 SDR 或已支持。
2. 优先原生解码与输出。设备、片源和显示路径兼容时不插入额外滤镜。
3. DV 降级依据真实兼容层信息。P8 不能一律视作 HDR10；P7 的基础层可播放不代表增强层完整处理。
4. 不支持原生播放时，只有在兼容基础层或转换路径被验证后，才声明已降级。没有可用路径时明确说明限制，并提供换源或退出，不能把偏色当成功。
5. 自动化只能声明观察到的事实。没有通用接口证实最终显示模式时，显示“输出模式未确认”，由电视信号信息和设备诊断完成验收。
6. 超分、普通高质量缩放、锐化和 SDR 转 HDR 分开命名。HDR/DV 默认保持原生路径，未经验证不叠加超分。
7. 自动增强根据输入分辨率、实际显示区域、GPU 能力及持续性能启用。原生分辨率已足够时不为显示一个开关而重复放大。
8. 任何取代 ADR-0039、ADR-0017 或相关决策的实现，先新增 superseding ADR；本方案不是已采纳的 ADR。

- [ ] 记录输入 codec、容器、位深、色彩传递函数、DV profile/level、兼容 ID 的值及来源；拿不到的字段显示未知。
- [ ] 记录解码器名称、硬解判断、当前显示器与其能力、实际视频尺寸、丢帧计数和采样时长。
- [ ] 将“请求开启增强”“滤镜配置成功”“效果已验证”分开，禁止以输出尺寸变化代替 AI 超分成功。
- [ ] 监听显示设备变化并重新探测，正确注册和注销监听器；播放中变化只触发一次重新评估，避免循环重建播放器。
- [ ] 导出报告时去掉播放 URL 的凭据、令牌、完整私有路径和设备唯一标识。

验收：换片后诊断清零；HDMI 变化后能力刷新；未知输出不显示已进入 DV；视频在线播放与 NAS 片库使用同一诊断逻辑。

### 3.1 播放器右上角显示当前片源标识

手机、电视、桌面内置播放器、mpv 和 Web/NAS 网页播放器均显示当前播放流的格式标识。与阶段 A 一起实现原生端与内置播放器，mpv 在阶段 C 接入同义 OSD。复用已有徽标与设计令牌，标识避开刘海、窗口按钮和其他浮层。

- 显示内容：分辨率（如 1080p、4K）、动态范围（Dolby Vision、HDR10+、HDR10、HLG），以及当前选中音轨已确认的音频规格（如 Dolby Atmos、TrueHD、DTS-HD）。普通 SDR 和普通音频不额外占位。
- 信息依据：当前播放流与选中音轨的真实元数据优先；当前文件的可信探测结果可补充。仅从片名或源站文案推测的格式不显示为已确认标识。未知字段不显示，不能将未知 HDR 类型默认显示为 SDR。
- Dolby Vision 片源回退 HDR10 时，片源标识保留 Dolby Vision，旁边明确显示“按 HDR10 播放”；仅在回退已被执行并确认后显示。无法确认最终输出时，详情显示“输出模式未确认”。
- 超分以独立状态标识显示；只开启开关或挂载滤镜时，不显示“AI 超分已生效”。原始 1080p 经放大仍标 1080p，不将处理后的尺寸当作原生 4K。
- 默认开播后短暂显示，之后随控制层显示和隐藏，避免长期遮挡画面；暂停和唤出控制层时可查看。音轨、视频流、清晰度、集数或播放源变化时重新计算，清除上一片源标识。
- Android 使用现有 `playbackBadges` 扩展纯函数和 `PlayerControls.kt` 渲染。Web 与桌面内置播放器复用 `UiSpecBadge`、`spec-badge.ts` 的映射；mpv 用播放器自身 OSD，不能把 Electron 浮层覆盖到外部窗口上。

验收：DV、HDR10+、HDR10、HLG、普通 SDR 分别显示正确；切音轨更新音频标识；换源与自适应视频轨变化后无旧标识；未确认输出不冒充 DV 已输出；手机触屏和电视遥控器均可唤出查看；HDR 画面上的标识清晰但不改变视频渲染路径。

## 4. 阶段 B：修正 HDR/DV 决策并落到实际播放

- [ ] NAS 已探测的片源信息可作为补充，但必须绑定当前具体文件和视频流，不能把同一电影的另一版本规格套用过来。

## 6. 阶段 D：安卓与电视超分原型

交付物：一个默认关闭、可恢复原生播放的 SDR 增强原型及性能报告。先证明可用，再将实验入口做成正式设置。

原型新增 `android/app/src/main/kotlin/com/yingbox/android/playback/engine/enhancement/`，包含增强策略和平台帧处理适配。依赖采用精确版本，与现有 Media3 对齐。

- [ ] 使用同一设备和片源先记录无增强基线；验证 Media3 视频效果接口能否在当前解码链中稳定工作。
- [ ] 先做普通 GPU 缩放与有限锐化，对外明确标为高质量缩放。
- [ ] 再选一个许可证允许分发的轻量模型，记录模型版本、文件大小、输入色域、输入位深和帧处理成本。没有通过模型验证前不承诺 AI 超分。
- [ ] 先测 SDR 720p 到 1080p，再测 SDR 1080p 到 4K。字幕在视频增强后合成，避免字幕参与模型处理。
- [ ] 核对硬解到 GPU 的拷贝次数、内存、帧延迟、功耗和温控。无法持续实时处理的设备自动退出增强，不影响基础播放。
- [ ] 单独测试电视已有画质增强叠加后的过锐和光晕。用户始终可关闭应用增强。
- [ ] HDR 扩展只在高精度颜色处理和 HDR 输出均可验证后进行；DV 原生路径继续旁路，除非能证明元数据和输出保持正确。

推进条件：30 分钟持续播放没有热降频导致的持续掉帧，画面没有明显闪烁、重影、光晕，关闭后恢复基线播放。若条件不满足，只保留普通缩放或标为不支持，不继续堆模型。

## 7. 阶段 E：Web、内置播放器和 NAS

交付物：支持的客户端获得可选增强，其余客户端清楚说明能力限制。NAS GPU 处理仅作为单独可选服务能力。

- [ ] Web 和 Electron 内置播放器先对受控 SDR 片源验证 GPU 视频处理、跨域、浏览器色彩管理、全屏和字幕；不支持时继续原生 video 播放。
- [ ] 用实际浏览器和 GPU 建立通过记录，不能只根据 WebGPU API 存在就认定实时超分可用。
- [ ] 对 DRM、无法访问帧或未知 HDR 输出的片源旁路增强。
- [ ] NAS 默认直放。用户选择服务端增强时，先探测 GPU、编码器和单路实时处理能力，再建立会话。
- [ ] 服务端方案必须包括会话鉴权、取消、资源限额、拖动重启、临时文件清理和失败回退；复用桌面重建的规则与经验，不能直接依赖 Electron 模块。
- [ ] 服务端转换输出标明为 SDR 或 HDR10；未实现保留 DV 元数据时不得标为 Dolby Vision。

阶段 E 的原型通过前，不承诺“全部设备实时 AI 超分”。替代交付是所有端共享一致的状态和开关语义，按能力开放。

## 8. 验收步骤和执行命令

准备有权使用的代表性片源，覆盖 SDR、HDR10、HLG、HDR10+、DV P5、P7、P8.1、P8.2、P8.4；覆盖 MP4、MKV 和实际线上 HLS。记录文件哈希、ffprobe 信息、来源和预期，不将大型片源或凭据提交仓库。

每组设备与片源执行：

1. 记录设备型号、系统、固件、解码器、显示器、HDMI 连接与是否经过功放。
2. 禁用增强，播放并核对颜色、暗部、高光、音画同步和实际显示模式。电视照片只证明模式标识，不作为精确色彩测量。
3. 拖动十次、切集五次、后台恢复三次，检查进度、声音、字幕和状态是否正确恢复。
4. 持续播放三十分钟，记录丢帧计数、采样时长、发热与错误。网络缓冲与 GPU 处理慢分开统计。
5. 对适用 SDR 片源开关增强，保持输出尺寸相同，比较画质、掉帧与功耗。若有处理耗时采样，以 P95 不超过单帧周期作为初始性能门槛；该门槛是验收目标，不是现有测量结果。
6. 模拟不支持格式、滤镜失败、显示变化和资源不足，验证能退出增强且不循环重试。

安卓在根目录执行 `pnpm build:android` 准备内嵌服务与 APK；在 `android` 目录执行 `./gradlew.bat :app:testDebugUnitTest :app:lintDebug`。预期构建与检查成功；真实 HDR/DV 验收使用安装后的 APK，不使用模拟器代替。

桌面迭代执行 `pnpm typecheck` 和 `pnpm test:affected`；集成前按 AGENTS.md 执行全量测试、构建与工程检查。真机运行实际 mpv 和内置播放器分别验收。

## 9. 实施顺序与发布条件

按 A、B、C、D、E 顺序推进。A/B 是第一批正式开发范围；C 利用现有实现补验收；D/E 是带退出条件的研究任务。设备型号和可用硬件确定后再估工期，不将未知平台支持折算成固定天数。

开始 A/B 需要收集安卓手机、电视或盒子型号、系统版本和 HDMI/功放连接方式。没有这些信息仍可实现纯逻辑与诊断，但不能完成设备兼容验收。

每阶段保留独立可运行的交付，记录已验证设备和未验证组合。代码交付前完成自审及项目要求的只读独立评审；有高风险未解决问题不发布。当前工作区已有 `android/gradle/gradle-daemon-jvm.properties` 未跟踪文件，实施时保留，不纳入本方案改动。
