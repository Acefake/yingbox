# 影盒 × lada：点开即看（边去马赛克边播放）设计

日期：2026-10-16
状态：待你确认（未开始实现）

---

## 1. 意图与为什么

你在影盒里看 JAV 片库时，希望：**点开一部片子就立刻开始看，画面里的马赛克已经（或正在）被 AI 修复**，而且**必须有声音**，不要"先跑几小时再回来看"。

去马赛克本身不是影盒能做的事——播放器做不到，它是**逐帧 AI 推理 + 重新编码**。这件事交给开源项目 **lada**（AGPL-3.0）来做，影盒负责编排与播放。

你已确认的两个关键取向：

- **点开就立刻看**（处理到哪看到哪），不是"跑完再存"
- **预先缓冲一些**：不必等你按下播放才开始跑，可以提前先跑着

## 2. 目标 / 非目标 / 反向目标

**目标**

1. 片库里对一部片子发起"修复"，能在**处理过程中**就开始观看
2. 全程**有声音**，且音画不漂移
3. 已经处理过的部分**不重复处理**（缓存可复用）
4. 影盒保持中文界面；lada 只作为外部工具

**非目标**

- 不做"实时逐帧修复"（lada 的 Watch 模式那种渲染管线）——我们走"落盘 + 播放增长文件"路线
- 不追求 4K（官方已知问题 + 你 6GB 显存）
- 不把 lada 打包进安装包
- **只覆盖本地片库**（磁盘上真有文件的那种）。在线 `/av` 板块拉的是远端流、磁盘上没有"原片"，不在本次范围内
- **不要求内置播放器可用**：本功能仅在 **mpv 引擎**下工作，界面负责引导用户切换引擎

**反向目标（这样算失败）**

- 音画越看越不同步
- 看着看着卡死、只能重开
- 处理中断后必须从头再来

## 4. 已验证的事实（实测，含证据）

1. **lada-cli 支持边写边播**：`--mp4-fast-start` 官方说明 *"Allows playing the file while it's being written"*，设置 `frag_keyframe+empty_moov+faststart`。
2. **lada 的输出是两段式的**（读 `lada/cli/main.py`）：先写**临时文件**（仅视频、无音轨），全部帧跑完后最后一步才把原片音频合并成正式文件；失败会删掉临时文件。
   → 所以"边看"的那份是**临时文件、纯视频**。
3. **mpv 能播放正在增长的分片 mp4**：实测把 30–60s 内容按 `frag_keyframe+empty_moov` 边写边播，mpv 打开正常、轨道识别正常、能持续消费新到达的分片。
4. **mpv 挂外挂音轨可行**：`--audio-file=<原片>` 会把它作为外部音轨挂上（日志 `--aid=2 ... [external]`），`audio-pts` 与 `time-pos` 差值稳定在 ~0.06s，音频确实经 WASAPI 输出到 Realtek 设备。
5. **相对 seek 不可靠**：增长文件的 `duration` 是过时的（实测一直报 10s），相对 seek 会跳到错误位置（实测倒退到 9.5s）。恢复必须用 `loadfile <文件> replace start=<位置>`。
6. **❌ 朴素方案会音画漂移（决定性失败）**：mpv 的 `--video-sync` 默认值是 **`audio`**——**音频是主时钟**。实测（音视频等长 30s、写入 0.35x）：
   - 播放位置由音频推进，视频数据先耗尽后画面停住，**音频继续往前播到结尾**
   - 播放器在视频 EOF 处自行暂停，日志形如 `audio=playing, video=eof (paused)`
   - 结论：**只要音频文件是完整的，它就会跑到视频前面**，靠"事后发现再纠正"必然产生可见的音画跳变

## 5. 方案对比

### A. mpv 播增长视频 + 外挂原片音轨 + 前沿控制器

播放器同时读"增长中的视频"和"完整的原片音轨"，由控制器在视频到达前沿时立刻暂停、等新数据、再 `loadfile start=` 续播。

- 优点：不需要额外封装进程，复用现成 mpv IPC
- 缺点：**与 mpv 的音频主时钟设计正面对抗**（见 4.6）；控制器一旦反应慢半拍就有音画跳变；`time-pos` 是音频时钟，不能当视频位置用

### B. 影盒做增量封装（推荐）

**分段封装，每段自带音视频**：

1. lada 往临时文件写视频（`--mp4-fast-start`，`frag_keyframe` 分片天然按关键帧对齐）
2. 每当临时文件长过上一段末尾，影盒就用 ffmpeg 切出这一段：视频取临时文件的该区间、音频取原片的同一区间，`-c copy` 封成一个分片（fMP4/TS），追加到 `index.m3u8`
3. 播放器播这个 **m3u8**（mpv 与影盒内置播放器都支持 HLS），到"直播边沿"自然等待

- 优点：
  - **每一段的音频和视频等长** → 音频在结构上不可能跑到视频前面，4.6 那类漂移直接消失
  - HLS 天然就是"边播边等"的形态，播放器侧不需要任何 hack
  - 分片 = 天然的缓存与断点，已处理段可复用、可跳转
  - 影盒已有 HLS 与 m3u8 播放经验
- 缺点：
  - 多一个 ffmpeg 封装步骤与状态管理；延迟增加约一个分片时长
  - 需要处理分段边界（关键帧对齐、音频切片精度）

**推荐 B。** 理由：A 是在跟 mpv 的时钟模型对抗，B 从结构上消灭了漂移；而且 B 顺带把"缓存/断点/跳转"全解决了——这对"处理很慢"这件事至关重要。

## 6. 已确认的取向（2026-10-16）

1. **片源范围**：**只做本地片库**——磁盘上有真实文件的片子。在线 `/av` 的远端流不在本次范围（那需要先加一整段"下载原片"流程）。
2. **播放引擎**：**仅 mpv**。内置播放器（Artplayer + hls.js）不要求支持本功能；界面负责引导用户切到 mpv 引擎。因此不需要为 Chromium 的 H.264/HEVC 兼容性妥协（可放心用 `hevc-nvidia-gpu-hq`）。
3. **是否分块喂 lada**：**尚未明确**。暂按"**不分块**"实现（整片跑，影盒自己记录已完成的成品文件作为缓存），把"分块"（换断点续跑 + 加急区间）留到以后。若这条要改，请直接说。

## 7. 我替你做的判断（请顺便核对）

- **不打包 lada**，只做外部工具集成（AGPL + 体积）
- 采用**方案 B**（分段封装 → HLS）
- 分片长度先取 **10 秒**（关键帧对齐，等待不至于太久）
- 进度条使用**原片时长**，不信任增长文件的 `duration`
- **播放期间 lada 继续跑**（否则"追播"没意义）；若检测到显存不足/掉帧，自动降级为"暂停处理，播完继续"
- **拖动只允许在已处理范围内**；不做到指定区间加急（留到以后，与第 6.3 问相关）
- **音频分片**：优先选默认音轨；若源音轨不是 AAC/MP3，则该段音频转码为 AAC（宁可多一点开销，也不能"没声音"）
- **ffmpeg 随包附带**（沿用 mpv 那套 `fetch-*` 脚本与 `resources/` 约定），同时支持在设置里覆盖路径；实现需锁最低版本
- 编码默认 `--encoding-preset hevc-nvidia-gpu-hq` + `--fp16`（因已确认仅 mpv，不必为 Chromium 的 HEVC 兼容性改用 H.264）
- 界面在发起/播放时检查当前引擎，若不是 mpv 则提示并引导切换（内置引擎明确不支持本功能）

**lada 已就位**

- `lada-cli.exe` / `lada.exe` → `%LOCALAPPDATA%\lada\lada\`，版本 **0.11.0**，解压后 5.52 GB / 5640 文件
- `--list-devices` 认出 `cuda:0 NVIDIA GeForce RTX 3060 Laptop GPU`；未显式传 `--device` 时走默认设备（即 cuda:0）
- 模型权重随包自带：修复 `basicvsrpp-v1.2`（推荐）/ `deepmosaics`；检测 `v2` / `v4-fast`（推荐）/ `v4-accurate`
- **lada 自带中文**：连 CLI 输出都是中文（"可用设备"、"快速高效，推荐"、"正在合并音频"）——之前"是否有中文"的疑问解决，且比 mpv 强得多

**吞吐基准（真实 1080p 片源，30 秒切片 / 899 帧，编码 `hevc-nvidia-gpu-hq`）**

|---|---|---|---|
| 源片 | 1080p，3.16 小时，6.5 GB | 1080p，1.19 小时，2.9 GB | 1080p，**70.3 分钟** |
| **启动 → 第一帧写出** | 23.5 秒 | 24.8 秒 | **36.6 秒** |
| 正式文件出现 | 44.2 秒 | 47.6 秒 | —（77.7 秒完成） |
| 总耗时（30s 素材） | 46.8 秒 | 49.6 秒 | **77.7 秒** |
| 等效实时倍率 | 1.56x | 1.65x | **2.59x** |
| **处理阶段速度** | **35.4 帧/秒** | **37.9 帧/秒** | **23.0 帧/秒** |
| 临时文件持续增长 | 是 ✅ | 是 ✅ | 是 ✅ |
| 输出 / 退出码 | 10.4 MB / 0 | 9.3 MB / 0 | 18.4 MB / 0 |

**修复是否真的生效：是。** 截取同一时刻帧对比确认——原片帧的马赛克像素块在输出帧里被重建为连续画面（"补"出来的，不是原片细节）。所以 23.0 帧/秒这个数字确实包含真实修复开销；相比无码内容的 35–38 帧/秒，**修复大约让速度降到 60%**。

### 缓冲公式（这就是"预先缓冲多久才够看"的答案）

有码内容处理 **23.0 帧/秒**，而播放需要 **29.97 帧/秒** → **处理追不上播放**：

- 每播放 1 秒，处理只能补上 23.0/29.97 = **0.767 秒** → 净亏 **0.233 秒/秒**
- 先预跑 T 秒，能连续观看 `0.767T / 0.233` ≈ **3.29T** 秒
- 要连续看完一部 L 秒的片子：**T ≥ L / 3.29 ≈ 0.30 L**

**结论：预跑约"片长的 30%"，之后可以连续看完不卡。**

| 片长 | 需要预跑 | 整片处理总耗时 |
|---|---|---|
| 30 分钟 | ≈ 9 分钟 | ≈ 39 分钟 |
| 1 小时 | **≈ 18 分钟** | ≈ 78 分钟 |
| 70 分钟 | ≈ 21 分钟 | ≈ 91 分钟 |
| 3.16 小时 | ≈ 58 分钟 | ≈ 4.1 小时 |

**这带来一个必须直面的现实**：对长篇（1 小时以上），"点开就立刻看"实际等于"先等 20 分钟左右才顺"，或者接受边看边停。设计上应当把预跑做成**自动的、入库就开始**，并把"当前缓冲到哪、预计会不会追上"如实显示给用户——而不是假装能即时观看。
