# 同一作品多个文件夹：合并展示与版本

同一部电影或剧放在两个（或多个）文件夹里，比如不同版本、不同盘，识别到同一个 TMDB id 后，片库只显示一次。详情页把各处的文件列成「版本」，默认播放最好的那个，可以切换。合错了可以拆开，拆分会保存下来。

目录层不变：每个文件夹仍是自己的本地条目，文件、NFO、整理计划都按本地条目算。合并只发生在展示层。

## 什么算同一作品

`media_items.merge_key`（虚拟生成列，迁移 v10，`src/main/library/db/schema-merge.ts`）：

| 条件                                                    | merge_key      |
| ------------------------------------------------------- | -------------- |
| 顶层条目、`tmdb_id` 不为空、匹配状态 `auto` 或 `locked` | `类型:tmdb_id` |
| 被手动拆出，且仍匹配着拆出时的 id                       | NULL           |
| 未匹配、待确认（`review`）、季 / 集                     | NULL           |

- 电影按 TMDB 电影 id，剧按 TMDB 剧 id；季、集不单独合并，在详情里按季号 / 集号对齐。
- 待确认的不合并：没把握的匹配合在一起，误合的代价比多显示一条大。
- 番号库的 `tmdb_id` 列存番号，所以同一番号也会在番号区合并。成员只在同一来源（TMDB 片库或番号库）的媒体库之间找。
- 生成列随 `tmdb_id`、`match_state`、`merge_split` 自动变，识别、手动匹配、锁定这些写入路径都不用改。

## 展示层

| 位置                            | 做法                                                                                                                                                                                      |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 海报墙 / 搜索 / 筛选（`query`） | `catalog/where-sql.ts`：一组同键条目里，满足**全部**筛选条件、id 最小的那条代表整组。所以只有另一份满足搜索或「只看某个媒体库」时，显示的就是那一份，整组不会因为代表条目不满足条件而消失 |
| 海报墙动态范围标                | 取整组所有文件里最好的一档                                                                                                                                                                |
| 分面计数（`facets.list`）       | `COUNT(DISTINCT COALESCE(merge_key, id))`，一部作品算一次                                                                                                                                 |
| 追剧日历                        | 每组只列 id 最小的剧；「本地有没有这一集」在所有成员里找                                                                                                                                  |
| 详情（`getItem`）               | `catalog/merge/merged-items.ts`：成员的树合成一棵，带版本和合并信息（下一节）                                                                                                             |
| 悬停预览                        | 用合并后的详情，取默认版本                                                                                                                                                                |
| 识别推送                        | 识别后并进别的组的条目，事件里额外记进 `added`，海报墙按结构变化重载可见区间（`identify/identify-events.ts`）                                                                             |

写出、整理、识别、演员仍读 `CatalogQuery.getItem` 的单个本地条目，不会把别的文件夹里的文件写进这个条目的 NFO 或整理计划。

## 详情：合并树与版本

`mergeTrees`（`catalog/merge/merge-tree.ts`，纯函数）：

- 元数据和 id 用打开的那个条目的，其余成员只贡献文件和它缺的季 / 集；
- 电影：文件并在一起；
- 剧：季按季号对齐，集按（季号, 集号）对齐（绝对集数挂在剧下，按集号对齐；按日期编号的按播出日期）。同一集在几处都有，文件并到同一个集节点，就是这一集的几个版本；某处独有的季 / 集直接接进来，所以两个文件夹各有部分集时合成完整的季；
- 同一集一份有元数据、一份没有时，用有元数据的那份当展示节点。

`buildVersions`（`catalog/merge/version-rules.ts`，纯函数），电影和集节点各算一次：

- **分组**：同一文件夹里带分段号（CD1 / part2，解析结果 `parsed.part`）的文件合成一个版本，按分段号播放；其余每个文件各是一个版本。这也修掉了老问题：同一个库里两个同名同年的文件夹本来就落到一个条目上，播放时会把两个版本当成分段接着放；
- **分辨率**：先看文件名（`2160p`、`1080i`、`3840x2160`、`4K`、`UHD`、`FHD`），没有再看所在文件夹名；
- **动态范围**：ffprobe 探测结果优先，没探测过时看文件名里的 `DV` / `DoVi` / `HDR10` / `HDR` / `HLG`（`HDRip` 不算）；
- **排序**：分辨率 > 动态范围 > 体积，都一样时按文件夹和文件 id，结果稳定。`versions[0]` 就是默认播放的。

契约：`LibraryItemNode.versions?: LibraryVersion[]` 和 `LibraryItemNode.merge?: ItemMergeInfo`（`shared/library/ipc/contract-merge.ts`）。`merge.members` 列出合并进来的本地条目和它们的作品文件夹（去掉末尾的 `Season 1` 这类文件夹）；`merge.splitFrom` 是被拆出的条目同一作品还有几处。

## 拆分与恢复（持久化）

- `merge.split({ itemId })`：`media_items.merge_split = tmdb_id`，这一条不再参与合并，单独出现在片库里；
- `merge.join({ itemId })`：清掉 `merge_split`，重新合并；
- 拆分记在条目上，重启、重扫都保留；条目改匹配到别的 id（修好误识别）后，`merge_split <> tmdb_id`，拆分自动失效，会按新 id 正常合并；
- 拆分 / 恢复都不改 `updated_at`（它晚于 `identified_at` 表示文件变了、要重新识别）；
- 推送：涉及的条目按库各发一条 `items-changed`，同时记进 `added` 和 `updated`：海报墙重载可见区间，打开着的详情重新取数。

## 界面（最小挂点）

详情页只加了一个区块 `detail/DetailVersions.vue`，放在「信息与文件」前面，样式只用现有 token 和 `UiButton` / `UiRadio`，留给 Apple TV 改版（详情页那一步）再定样式：

- 电影有多个版本时：每个版本一行（`2160p · DV · 23.4 GB` + 来源文件夹），单选；合并了多处时每处给一个「拆出」；
- 剧合并了多个来源时：「自动：每集用最好的版本」+ 每个来源一行（`12 集 · 最高 2160p · 40 GB` + 文件夹）。选了某个来源后，每集优先用这个来源里最好的版本，那里没有的集退回整体最好的；
- 被拆出的条目：一行「已单独显示，同一作品另有 N 处文件 · 恢复合并」。

播放规则在 `detail/version-rules.ts` 和 `detail/playback.ts`：`videoFileEntries(node, prefer)` 返回选中版本的文件，所以视频墙、悬停卡、去码、片头识别这些只拿节点的入口都自动用默认版本。选择只在当前详情里记着，换条目回到默认。详情里的「刷新元数据」「写出」对全部成员做；「整理」「锁定」「修正匹配」仍只对打开的条目做。

## 性能

基准方法沿用 [baseline.md](./baseline.md)：同形的假库，5 万文件、6560 个顶层条目，电影库加剧集库。`pnpm bench:library` 的引擎部分新增了「合并展示」表：把全部顶层条目标成已匹配，再让 20% 两两共用 TMDB id，重跑同一组查询形态，另测一部合并剧的详情。

这台机器测量时负载很高（2 vCPU，load average 约 8，同时跑着别的构建和测试），绝对值比 baseline.md 大几倍，波动也大。所以另做了一个**同进程交替 A/B**：同一个库、同一进程里，main（4ca24d8）的列表 SQL 和本分支 `CatalogQuery.list` 交替各跑 15 次，取中位数。单位 ms，第二次运行：

| 查询                     | 未识别 · main | 未识别 · 本分支 | 已匹配 20% 成对 · main | 已匹配 20% 成对 · 本分支 |
| ------------------------ | ------------: | --------------: | ---------------------: | -----------------------: |
| 默认（片名升序，200 条） |          41.6 |            14.4 |                   21.8 |                     21.0 |
| 按添加时间降序           |         669.1 |            28.8 |                  591.9 |                     39.3 |
| 按年份降序 + 年份区间    |           9.6 |             4.9 |                   15.5 |                     12.5 |
| 只看剧集                 |         339.7 |            17.2 |                  427.0 |                     23.4 |
| FTS 搜索「Movie 12」     |           3.8 |             4.4 |                    2.6 |               4.7–14.9 ¹ |
| 短词搜索（LIKE）「12」   |           5.4 |             7.5 |                   15.4 |                     17.5 |
| 深分页 offset 5000       |          22.6 |             8.4 |                   49.7 |                     35.3 |

命中总数：已匹配时 main 6560 条，本分支 5904 条（656 对各算一次）。

¹ 两次运行分别是 4.7 和 14.9，在这台机器的噪声范围内；单独测 SQL 是 2.4 ms。

几处数字的来源：

- **按添加时间 / 只看剧集，main 要 0.3–1 秒**：这是 v8（动态范围小标）就有的问题，跟合并无关。`range_rank` 子查询里 `fm.item_id = i.id OR fm.item_id IN (…)` 的 OR 让 `file_media` 走全表扫描，一部剧一遍；排序用不上索引时（多类型按添加时间、只看剧集），排序前对每个命中行都要算一次。本分支两处改动：先只排序取这一页的 id，再给这 200 条取列表列；`range_rank` 改成先列出整组节点（成员、子、孙）再按 `file_media(item_id)` 索引取文件。
- **去重探测**：`(i.merge_key IS NULL OR NOT EXISTS (SELECT 1 FROM media_items o INDEXED BY media_items_merge WHERE o.merge_key = i.merge_key AND o.id < i.id AND <同一套条件>))`。部分索引 `media_items_merge(merge_key, id) WHERE merge_key IS NOT NULL` 只收有键的行，未识别的条目一行都不探测。`INDEXED BY` 把探测钉在这个索引上，免得来源 / 媒体库条件把它带去别的索引。
- **FTS**：命中集写成物化 CTE `fts_hits`，i、o 两边共用一次全文检索。o 一侧写成 `+o.id IN fts_hits`：一元 + 让这一项只做成员判断，否则规划器会拿命中集逐个去探 merge 索引（一次搜索 5 ms 多出来就是这个）。
- **小查询多 1–3 ms**：列表变成两步（排序取 id、再取列），结果很少时固定开销占比显得大，仍远低于 200 ms 目标。
- **合并详情**：一部 100 集的剧加上另一个文件夹里的同一部剧，`getItem` 合并后约 27 ms，同一部剧不合并约 13 ms（同样受机器负载影响）。主要多在第二棵树的读取，以及每集的版本分组。

A/B 脚本没进仓库（它要手抄一份 main 的 SQL，合并以后就没有意义了），数字可以用 `pnpm bench:library --skip-scan --skip-parse` 的「查询形态」和「合并展示」两张表在空闲机器上复测。

- `tests/library/ui/version-rules.test.ts`：默认播放最好的版本、不把别的版本接着连播、切换与失效退回、剧集按来源优先、展示文字。

## 没做

- 分辨率只从文件名 / 文件夹名读；ffprobe 已经在探测动态范围，但没有存视频高度。文件名里没写分辨率的版本按动态范围和体积排。要准确的话，给 `files` 加一列高度，在动态范围探测里顺手写入，已探测过的文件要重探一遍；
- 没有「手动合并」（把两个 id 不同的条目合成一个）：现在靠修正匹配到同一个 id；
- 同一个本地条目里的多个文件（同库同名同年的两个文件夹）只能选版本，不能拆：它们按本地片名 + 年份落在一个条目上，跟 TMDB 合并无关；
- 选中的版本 / 来源不记住，换条目或重开详情回到默认；
- 剧集的版本只能按来源整体切换，不能单独给某一集挑版本；
- 海报卡片上没有「多个版本」的角标；
- 「继续播放」按打开的那个条目 id 记，从另一份打开同一作品时进度不共享；
- 未在真机（Windows / NAS / 网盘）上验证，详情区块也没截图。
