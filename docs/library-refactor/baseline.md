# 媒体库重构 P0 基准

本文记录电影 / 电视剧重构开工前的基准，以及 P1（解析 + 识别核心、扫描器修复）之后的对比。
所有数字都可以用 `pnpm bench:library` 复现（脚本：`scripts/bench-library.ts`）。

## 测量环境

- Linux 容器，2 vCPU，overlay 文件系统，Node v22.23.3。
- 假媒体库建在系统临时目录，文件都是空文件，跑在页缓存上。所以“冷扫”指**没有旧索引**的全量扫描，
  不是冷磁盘；Windows / NAS / OneDrive 上 stat 更贵，绝对值会大很多，但前后对比的倍数关系不变。
- 解析耗时受机器噪声影响，多次运行在 20–30 µs/条（预热后）之间浮动。

## 扫描（src/main/media-scanner.ts）

假库布局：根目录下直接放 6250 个电影文件夹（视频 + nfo + poster，每 10 部带 Featurettes）和
295 部剧（4 季 × 25 集，最后一部不满），共 50000 个文件、8347 个目录。“深层变更”是在某部剧的 `Season 2`
里新增一集、删除一集，剧目录自身 mtime 不变。

| 场景             |                                               修复前 |                   修复后 |
| ---------------- | ---------------------------------------------------: | -----------------------: |
| 冷扫（无旧索引） |                                               741 ms |               704–832 ms |
| 热扫（目录未变） |                                         **42096 ms** |           **194–199 ms** |
| 深层变更后热扫   | 51363 ms，新增文件**未发现**、删除文件**仍在结果里** | 172–178 ms，正确发现增删 |

修复前只跑了 1 次（单次热扫 42 秒，3 次会超时）；修复后取 3 次中位数，两次独立运行的范围如上。

规模扩展（修复前单次 / 修复后 3 次中位数）：

| 文件数 | 修复前热扫 | 修复后热扫 |
| -----: | ---------: | ---------: |
|  12500 |    2689 ms |      57 ms |
|  25000 |   10877 ms |     109 ms |
|  50000 |   42096 ms |     199 ms |

文件数翻倍，修复前热扫约 ×4（平方级），修复后约 ×2（线性）。

### 原因

1. **目录 mtime 短路复用了整棵子树。** 目录 mtime 只在它的直接子项增删改名时变化，孙子层的变化不会
   反映上来。原实现命中短路后复用该目录下全部缓存后代，于是 `剧/Season 2` 里的新集永远扫不到，删掉的集
   永远留在结果里。
2. **collectCachedDescendants 是 O(目录数 × 条目数)。** 每个命中短路的目录都全量遍历一次旧索引做前缀匹配；
   根目录下 6545 个目录 × 58347 条索引 ≈ 3.8 亿次字符串比较，这就是热扫 42 秒的来源。

### 修复

- 命中短路时只复用该目录的**直接文件**子项，子目录照常 stat、各自判断是否短路。热扫因此要 stat 全部
  8347 个目录，但不 stat 任何文件。
- 旧索引按父目录分组建表，复用一个目录的代价与其直接子项数成正比。
- 顺带：目录处理改为 16 路并发池（原来是 4 个一批、等最慢的那个），目录内文件 stat 并发发起，结果排序改用
  复用的 `Intl.Collator`（排序结果与 `localeCompare` 一致）。冷扫在这台机器上没有明显变化（页缓存上 stat
  很便宜）；在高延迟文件系统上并发的收益会更明显，P2 引擎上线后在真实库上复测。

回归测试：`tests/media-scanner.test.ts` 新增两条（孙子层增删可见；短路目录复用直接文件但仍下钻子目录），
修复前都失败，修复后通过。

按来源：手写难例 118/119，留出集 74/74，规则生成 5398/5398。

**留出集第一次运行是 70/74（94.6%）**，失败的 4 条暴露了 4 个通用问题，修复后 74/74：

- “封神第一部”里的“第一部”被当成季号（中文季号不再接受“部”）；
- “Extra-Terrestrial”因为 `extra` 是附加内容关键字被拆开（附加内容词只认作后缀）；
- 字幕组常用的 `Title S2 - 12` 被当成绝对集数（新增“季 + 集”写法）；
- 片名后的多词说明 `- Behind the Scenes` 没被识别为附加内容。

所以 74/74 已不是“盲测”数字；对未见过写法的泛化能力，更接近首跑的 94.6%。

唯一未通过：`Reply 1988 S01E05`（剧名以年份形式的数字结尾）。仅凭文件名和文件夹名无法区分“片名里的 1988”
与“年份 1988”（同形的 `Doctor.Who.2005.S01E01` 里 2005 是年份）。识别阶段可以用“带年份 / 不带年份各搜一次”
兜底，留到 P3。

### 与 @ctrl/video-filename-parser 的对比

同一黄金集，只给文件名，并且**额外告诉它是不是剧集**（它需要调用方传 `isTv`）：

| 指标                     | @ctrl/video-filename-parser 5.12.0 |       本 PR 解析器 |
| ------------------------ | ---------------------------------: | -----------------: |
| 片名（允许中英拼在一起） |                              61.1% |              99.9% |
| 集号（剧集）             |                              78.9% |             100.0% |
| 年份                     |                              61.6% |             100.0% |
| 单条耗时                 |                             ~80 µs | 20–30 µs（预热后） |

它在纯英文场景名上表现不错（movie-scene 片名 89%、1x01 / EP 近 100%），主要差在：中文片名与中文季集
（episode-cjk 片名 1.9%）、通用文件名与光盘结构（不看文件夹，0%）、中文字幕组动画（64%）、附加内容
（没有这个类型）。这些恰好是本项目用户库的主体，所以没有采用，见 PR 说明。
