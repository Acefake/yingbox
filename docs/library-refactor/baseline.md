# 媒体库重构 P0 基准

本文记录电影 / 电视剧重构开工前的基准，以及 P1（解析 + 识别核心、扫描器修复）之后的对比；末尾是 P2（媒体库引擎）的基准。
所有数字都可以用 `pnpm bench:library` 复现（脚本：`scripts/bench-library.ts`）。

## 测量环境

- Linux 容器，2 vCPU，overlay 文件系统，Node v22.23.3。
- 假媒体库建在系统临时目录，文件都是空文件，跑在页缓存上。所以“冷扫”指**没有旧索引**的全量扫描，
  不是冷磁盘；Windows / NAS / OneDrive 上 stat 更贵，绝对值会大很多，但前后对比的倍数关系不变。
- 解析耗时受机器噪声影响，多次运行在 20–30 µs/条（预热后）之间浮动。

## 扫描（src/main/media-scanner.ts）

假库布局：根目录下直接放 6250 个电影文件夹（视频 + nfo + poster，每 10 部带 Featurettes）和
295 部剧（4 季 × 25 集，最后一部不满），共 50000 个文件、8347 个目录。“深层变更”是在某部剧的 `Season 2`
里新增一集、删除一集，剧目录自身 mtime 不变。

| 场景             |                                               修复前 |                   修复后 |
| ---------------- | ---------------------------------------------------: | -----------------------: |
| 冷扫（无旧索引） |                                               741 ms |               704–832 ms |
| 热扫（目录未变） |                                         **42096 ms** |           **194–199 ms** |
| 深层变更后热扫   | 51363 ms，新增文件**未发现**、删除文件**仍在结果里** | 172–178 ms，正确发现增删 |

修复前只跑了 1 次（单次热扫 42 秒，3 次会超时）；修复后取 3 次中位数，两次独立运行的范围如上。

规模扩展（修复前单次 / 修复后 3 次中位数）：

| 文件数 | 修复前热扫 | 修复后热扫 |
| -----: | ---------: | ---------: |
|  12500 |    2689 ms |      57 ms |
|  25000 |   10877 ms |     109 ms |
|  50000 |   42096 ms |     199 ms |

文件数翻倍，修复前热扫约 ×4（平方级），修复后约 ×2（线性）。

### 原因

1. **目录 mtime 短路复用了整棵子树。** 目录 mtime 只在它的直接子项增删改名时变化，孙子层的变化不会
   反映上来。原实现命中短路后复用该目录下全部缓存后代，于是 `剧/Season 2` 里的新集永远扫不到，删掉的集
   永远留在结果里。
2. **collectCachedDescendants 是 O(目录数 × 条目数)。** 每个命中短路的目录都全量遍历一次旧索引做前缀匹配；
   根目录下 6545 个目录 × 58347 条索引 ≈ 3.8 亿次字符串比较，这就是热扫 42 秒的来源。

### 修复

- 命中短路时只复用该目录的**直接文件**子项，子目录照常 stat、各自判断是否短路。热扫因此要 stat 全部
  8347 个目录，但不 stat 任何文件。
- 旧索引按父目录分组建表，复用一个目录的代价与其直接子项数成正比。
- 顺带：目录处理改为 16 路并发池（原来是 4 个一批、等最慢的那个），目录内文件 stat 并发发起，结果排序改用
  复用的 `Intl.Collator`（排序结果与 `localeCompare` 一致）。冷扫在这台机器上没有明显变化（页缓存上 stat
  很便宜）；在高延迟文件系统上并发的收益会更明显，P2 引擎上线后在真实库上复测。

回归测试：`tests/media-scanner.test.ts` 新增两条（孙子层增删可见；短路目录复用直接文件但仍下钻子目录），
修复前都失败，修复后通过。

## P2 媒体库引擎（src/main/library）

引擎跑在 Electron utilityProcess 里，SQLite（Node 内置 `node:sqlite`，WAL）存目录、文件、解析结果和本地条目。
数字用 `pnpm bench:library --skip-scan --skip-parse` 复现；测量环境同上（Linux 容器、2 vCPU、页缓存上的空文件），
基准脚本直接调用引擎模块（与 utilityProcess 里运行的是同一份代码，不含进程间消息开销，单次调用 < 1 ms）。

假媒体库：50000 个文件、8347 个目录，拆成电影库（Movies/）和剧集库（TV/）两个媒体库；
目录 mtime 预先拨回一小时前。数据库为临时目录里的文件（WAL）。每项取 3 次中位数。

| 场景                     | 耗时 (ms) |   目标 | 说明                                                                 |
| ------------------------ | --------: | -----: | -------------------------------------------------------------------- |
| 冷扫入库                 |      3910 |      — | 写入 50000 个文件、6545 个顶层条目；遍历 782 ms，解析 + 写库 3143 ms |
| 无变化重扫               |       126 | < 1000 | 只 stat 目录，零写入                                                 |
| 深层变更重扫（剧集库）   |        32 |      — | 新增 1、删除 1                                                       |
| 首屏查询（新连接第一次） |       8.1 |  < 200 | 默认排序 200 条 + 总数                                               |

| getItem（一部剧）        |      4.37 |      — | 4 季 100 集，含文件                                                  |

### 数字说明

- **无变化重扫 126 ms**：只 stat 全部 8347 个目录（目录 mtime 未变 → 不 readdir、不 stat 文件），快照里的目录表
  一次读入内存，零写入。P1 修好的扫描器热扫是 ~199 ms，多出来的是它要返回并排序 5.8 万条结果；引擎只产出差异。
  目录 mtime 是“预先拨回一小时前”的：扫描时刚被改过（3 秒窗口内）的目录 mtime 不可信，会记成哨兵值下次强制重读
  （防止同一时间片内的第二次改动被漏掉），刚生成的假库如果不拨回，第一次重扫会把全部目录都重读一遍。
- **冷扫入库 3.9 s**：遍历 0.8 s（与 P1 冷扫一致），其余是解析 + 写库。CPU 剖析里解析器约 0.5 s，SQLite 插入
  占大头（文件行 5 万条带 6 个索引、条目 3.7 万条带 7 个索引和 FTS 触发器），每 2000 个文件一个事务，批间让出事件循环，
  扫描期间查询照常响应。
- **首屏查询 8 ms**：默认排序（片名）取 200 条 + 总数。“新连接第一次”是关闭数据库后重新打开的第一次查询，包含语句编译；
  操作系统页缓存是热的，冷磁盘上首次会更慢，但仍远低于 200 ms 目标。主要开销是 200 行的对象构造和 COUNT。
- 两项目标（首屏查询 < 200 ms、无变化重扫 < 1 s）都达到。真实 Windows / NAS 上 stat 更贵：无变化重扫的成本
  与目录数成正比（每个目录一次 stat），需要在真实库上复测；冷扫的遍历部分同样受网络延迟影响。
