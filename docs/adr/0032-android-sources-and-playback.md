# ADR-0032 安卓详情选源：服务端会话轮询，播放走服务端代理

- 日期：2026-11-02
- 状态：已采纳
- 相关：ADR-0028（安卓端方案）、ADR-0030（视图域）、ADR-0031（播放记录存服务端）、ADR-0019（服务端播放代理）

## 背景

安卓首页能打开豆瓣卡之后，下一步是详情、选源和播放。桌面详情页的做法（`features/online/composables/use-detail-sources.ts`、`use-online-search.ts`）：按片名并发搜所有启用的 CMS 与插件站点，片名匹配的条目再取线路，结果陆续出现；插件剧集要再让插件解析出真正的播放地址，页面地址要从 HTML 里找 m3u8。一次搜索要几秒到十几秒，必须边搜边出结果。

这些步骤的规则大多是纯函数，写在渲染层，依赖 `utils/json.ts`、`utils/vod-data.ts`。

## 决策

1. **规则搬进共享代码。** `json`、`concurrency`、`vod-data`、`vod-payload`、`site-selection` 与在线条目的类型移到 `src/shared`；`detail-sources` 里片名匹配、去重、按站点分组的部分移到 `src/shared/online/sources.ts`，拼播放器队列的部分留在渲染层；播放地址解析改成注入式（`src/shared/online/play-source.ts`）。函数的调用方全部改为直接导入新位置，不留转手文件；在线条目的类型沿用 `features/online/types.ts` 已有的转出方式（与 ADR-0030 相同）。
2. **选源用服务端会话。** `view.sourcesStart(片名)` 在服务端后台开始搜并立即返回会话的当前结果，客户端用 `view.sources(会话 ID)` 轮询，每次拿到当前结果的整份快照（结果没变时服务端不重算），直到 `done`。同一部片（归一化片名）10 分钟内复用会话；结束却一个源都没找到的会话不复用。一次选源最长 90 秒，到点收尾；客户端 15 秒没来取结果就当它离开了详情页，剩下的站点不再请求；最多保留 20 个会话。搜索步骤与桌面相同，站点默认是 `cms-sites.json` 的全部 CMS 站点加引擎给出的全部非成人插件站点；用户自己的启用列表等设置同步后接入。
3. **播放走服务端播放代理。** `view.resolve(剧集)` 用共享规则解析出媒体地址，返回 `/api/stream?src=…` 代理路径与是否 HLS。代理按来源补防盗链 Referer、改写 m3u8 里的分片地址；客户端只需给每个请求带上令牌。
4. **续播从记录取。** 安卓每次开播先 `playback.continueStart` 登记，再用 `view.resume(记录 ID)` 取剧集、当前集和起始秒数；同一集已有进度就接着播，规则就是共享的 `startRecord`。继续观看的 `key` 与桌面一样用片名，换源后仍是同一条记录。

## 后果

- 安卓只解析生成的视图类型；选源、解析、续播的规则与桌面同一份。
- 轮询比推送多几次请求（每 0.8 秒一次，搜完就停），换来不用为单个页面维持事件流。
- 健康度熔断（`cms-health`、插件健康度）暂未接入服务端选源，靠 CMS 每站 10 秒、插件每次 45 秒的超时与整体 90 秒时限兜底；坏源多时搜索会慢，后续接入。
- 测速排序（`use-source-probe`）暂未接入，站点按找到的先后排列。
- HLS 判断看解析出的地址是否以 `.m3u8` 结尾；没有后缀的清单会被当成普通文件，播放失败时客户端提示换源。`direct=false`（解析不出媒体直链）目前客户端没有单独处理，同样靠播放失败的提示。
- 轮询每次回整份快照，长剧加几十个站点时一次可能有几百 KB；需要时再改成按版本只回变化。

## 否决方案

- **客户端直接调 `online` 原子接口自己拼**：选源规则要在 Kotlin 里重写一遍。
- **一次调用等全部结果**：要等最慢的站点超时，十几秒没有任何反馈。
- **SSE 推送选源进度**：服务端已有域事件流，但它是全局广播，要为会话做订阅过滤；轮询更简单，且搜完即停。
- **客户端直连媒体地址**：防盗链 Referer、m3u8 里的相对地址都要在客户端重新处理，网页端已经靠代理解决。
